## 0. 이번 단계에서 하려는 일

> **기능을 정하는 게 아니라, "무엇을 알려줄지 → 왜 알려주는지 → 그래서 무엇을 하게 할지"를 하나로 묶는 기준을 정하는 단계.**

신호를 하나씩 따로 기획하면, 신호마다 판단 기준과 문장 투와 필요한 정보가 제각각이 된다. 그러면 개발자에게 넘길 때 전부 다시 이야기해야 한다.
그래서 이번에는 **신호를 담는 틀(=엑셀 한 장의 열 구조)을 먼저 정하고**, 그 틀에 맞춰 신호를 채운다. 틀이 정해지면 신호를 늘리는 일은 칸을 채우는 단순 작업이 된다.

이번 단계에서 답해야 하는 것 4가지

1. 무엇을 **알려줄 만한 변화(신호)** 로 볼 것인가
2. **왜 알려주는지(근거)** 를 무엇으로 보여줄 것인가
3. 알림을 본 사람이 **무엇을 하게 할 것인가(행동)**, 그 결과는 어디에 남는가
4. 같은 변화가 **여러 사람에게 각각 다르게 보여야 할 때**, 누구에게 어떻게 보여줄 것인가

## 1. 적용 대상 — 네 주체

| 주체 | 누구인가 | 무엇을 기준으로 보는가 | 알고 싶어하는 것 | 하게 될 행동 |
|---|---|---|---|---|
| **조직원** | 본인 성과의 당사자 | 나 자신 | 내가 할 일 / 내가 놓친 것 | 직접 쓰고 고치기 |
| **조직장 (1차 평가자)** | 직속 구성원의 평가·육성 책임자 | 팀원 한 사람씩 | 팀원별로 챙길 것 | 챙기고 독려하고 1차 판단하기 |
| **조직장 (2차 평가자)** | 하위 조직과 1차 평가자를 검토하는 상위 조직장 | 팀 단위 / 1차 평가자 | 팀 간 차이, 1차 평가의 충실도 | 조정 요청·재검토 요구·승인 |
| **HR 및 경영진** | 제도 운영자와 전사 의사결정자 | 조직 전체 | 진행률, 등급 분포, 제도에서 벗어난 곳 | 진단·독려·정책 판단 |

### 여기서 나오는 세 가지 판단

1. **2차 평가자가 보는 대상은 "사람"이 아니다.** 1차 평가자는 팀원 개인을 보지만, 2차 평가자는 *팀 단위로 합친 수치*와 *1차 평가자가 어떻게 평가했는지*를 본다. 보는 대상이 다르니 알림도 따로 만들어야 한다. **네 주체 중 지금 가장 준비가 안 된 칸이며, 이번에 가장 많이 고민해야 할 대상.**
2. **1차와 2차를 나눈 순간, 중복 알림 문제가 생긴다.** 같은 팀원 건이 1차·2차에 동시에 뜨면 2차 평가자에게는 잔소리가 된다. §3의 "누구에게 보여줄지 정하는 규칙"이 이걸 막는다.
3. **HR과 경영진은 보는 범위는 같고 할 수 있는 일이 다르다.** HR은 제도 운영, 경영진은 조직·자원 판단. 알림은 같이 쓰고 행동 칸만 다르게 쓴다.

## 2. 이미 정해진 것 (다시 논의하지 않음)

| # | 정해진 것 | 이유 |
|---|---|---|
| P1 | 화면에 뜨는 형태는 **알림 카드 한 종류**. 위에 신호, 가운데 근거, 아래 행동 | 주체별·단계별로 다른 화면을 각각 만들면 수십 개가 되고, 그래도 특별할 게 없다 |
| P2 | **무엇을 알릴지 고르는 일은 시스템 규칙이 하고, 문장 다듬기와 초안 쓰기만 AI가 한다** | 전 직원 데이터를 AI에 계속 넣어 "여기 문제 있나?"를 묻는 방식은 비용이 크고, 같은 상황에서 답이 달라지고, "왜 이 알림이 떴는지" 설명을 못 한다. 성과관리에서는 설명이 안 되면 쓸 수 없다 |
| P3 | **휴넬 안에 넣는다** | 조직·직무·발령 정보를 가진 곳에서만 우리만 할 수 있는 알림이 나온다 |
| P4 | **업무보드는 범위에서 제외** | 휴넬에 얹는 구조이므로 |
| P5 | 근거와 초안 재료는 **시스템에 실제로 있을만한 정보**로만 | 정보가 없는 알림은 기획서에만 존재한다 |
| P6 | AI는 **초안까지만**, 최종 확정은 사람이 | 사람 확인 없이 자동으로 처리되면 성과관리에서 신뢰를 얻지 못한다 |

> **빠진 항목 — "짧은 기간에 개발 가능한지"**
> 지금 단계에서 볼 일이 아니다. 개발 난이도로 신호를 미리 지우면 기획이 일정에 끌려간다. 만들기 어려운 항목은 엑셀의 비고 칸에 "확인 필요"로만 적어 둔다.

## 3. 신호·근거·행동을 정하는 기준

### 3.1 무엇을 신호로 볼 것인가

> 신호 = ① 무언가 달라졌고, ② 그 변화 때문에 특정한 사람이 무언가를 해야 하고, ③ 그 판단을 시스템 규칙으로 할 수 있는 경우.

세 가지 중 하나라도 빠지면 알림으로 만들지 않는다.
②가 없으면 그냥 현황 조회로 충분하고, ③이 없으면 시스템이 판단할 수 없다(P2와 맞지 않는다).

**변화의 종류 5가지 — 신호 후보를 뽑는 기준**

알림거리는 결국 아래 5가지 중 하나다. `(변화의 종류) × (무엇을 보는지)` 를 조합해 후보를 뽑는다. 5가지를 순서대로 훑으면 빠뜨리는 게 확실히 줄어든다.

| 구분 | 어떤 변화인가 | 판단에 필요한 정보 | 우리만 할 수 있는 정도 |
|---|---|---|---|
| **① 때가 됐다** | 기간이 열렸거나 마감이 다가옴·지났음 | 평가·목표 기간 일정 | 낮음 (어느 시스템이나 함) — **기초 알림의 주력** |
| **② 비어 있다 / 멈췄다** | 써야 할 게 안 써졌음 / 며칠째 그대로임 | 마지막으로 고친 날짜 | 중간 |
| **③ 기준을 벗어났다** | 수치가 기준선 밖으로 나감 | 수치 + 비교 기준 | 중간~높음 (비교 기준이 조직 데이터면 높음) |
| **④ 서로 안 맞는다** | 내 목표가 팀 목표·내 직무와 어긋남, 평가와 근거가 안 맞음 | 목표·조직·직무의 연결 관계 | **높음** — 조직·직무 정보가 있어야 가능 |
| **⑤ 무슨 일이 생겼다** | 발령, 조직 개편, 피드백 도착, 같이 걸린 동료의 진행 | 변경 이력 | **매우 높음** — 휴넬만 가능 |

- *"아주 기초적인 것부터"* 라는 요구는 ①②로 채운다. 만들기 쉽고 안정적이며, 알림 목록이 비지 않게 받쳐 준다.
- *우리만 할 수 있는 알림*은 ④⑤에서만 나온다. ④⑤가 없으면 결국 마감 알림 모음이 된다.
- 칸마다 ①~⑤를 다 훑되, 실제 채택은 아래 점수 기준으로 걸러낸다.

**누구에게 보여줄지 정하는 규칙**

같은 변화라도 주체별로 다른 알림이 된다. 다만 무조건 네 사람에게 다 뜨는 게 아니다.

| 주체 | 이 사람에게 알림이 되는 조건 |
|---|---|
| 조직원 | 변화의 대상이 **나 자신**일 때. 남의 변화는 *나와 어떻게 연결되는지 근거를 댈 수 있을 때만* (예: 내 목표에 같이 걸린 동료) |
| 조직장(1차) | 변화의 대상이 **직속 팀원 한 사람**일 때 |
| 조직장(2차) | 개별 팀원 건은 올리지 않는다. **팀 단위로 합친 수치** 또는 **1차 평가자가 한 일**만 |
| HR·경영진 | **조직·전사 단위로 합친 수치**, 진행률, 제도에서 벗어난 곳. 개인은 되도록 특정하지 않는다 |

**위로 올릴 때의 조건 3가지** — 아래 셋이 모두 맞을 때만 상위 주체에게도 알림을 만든다.

1. **합쳐서 볼 수 있는가** — 개별 건을 그대로 올리면 상위 주체에게는 소음이다
2. **아래 사람이 먼저 처리할 기회를 가졌는가** — 팀장이 볼 기회도 없이 HR에 먼저 뜨면 제도에 대한 신뢰가 깨진다
3. **상위 주체가 실제로 할 수 있는 일이 있는가** — 없으면 "볼 건 많은데 할 건 없는" 알림이 된다

> 3번이 이번 기획의 가장 어려운 부분이다. HR·경영진 알림은 "그냥 들여다보기"로 끝나기 쉽다. §3.3의 행동 종류에서 상위 주체용 결과 저장 위치를 반드시 지정한다.

**너무 자주 뜨지 않게 막는 규칙 4가지**

규칙으로 만든 알림이 미움받는 이유는 못 찾아내서가 아니라 **너무 자주 떠서**다. 아래 4가지는 숫자까지 정한다.

| 규칙 | 내용 | 안 정하면 |
|---|---|---|
| **재알림 간격** | 같은 사람에게 같은 알림은 며칠 안에 다시 띄우지 않는다 | 같은 알림이 매일 뜬다 |
| **상위 알림이 있으면 생략** | 같은 원인으로 위쪽에 알림이 떴으면 아래쪽 중복 알림은 만들지 않는다 (반대 방향도 정한다) | 1차·2차에 같은 건이 두 번 뜬다 |
| **처리하면 사라짐** | 사용자가 행동을 마치면 즉시 없어지고 결과만 기록에 남는다 | 이미 처리한 알림이 계속 남아 있다 |
| **최소 건수** | 합쳐서 보는 알림은 몇 건·몇 % 미만이면 띄우지 않는다 | 2차·HR 알림이 항상 떠 있다 |

이 숫자들은 신호 목록을 채우기 **전에** 정한다. 알림을 먼저 늘리고 나중에 막으려 하면 이미 과하게 뜨는 구조가 굳는다.

**채택 기준 3가지와 컷라인**

| 기준 | 질문 | 점수 |
|---|---|---|
| ① 도움이 되는가 | 놓치면 아쉬운 알림인가 | 크다 3 / 보통 2 / 작다 1 |
| ② 자주 생기는가 | 드물면 알림 목록이 빈다 | 자주 3 / 보통 2 / 드묾 1 |
| ③ 우리만 가능한가 | 휴넬 정보가 있어야만 알 수 있는가 | 그렇다 3 / 일부 2 / 아니다 1 |

- 합계 **6점 미만은 제외**
- **③이 1점인 알림은 "기초"로 분류**하고 칸마다 1개까지만 (마감 알림류가 목록을 다 차지하는 것을 막는다)
- 칸별 목표 = **기초 1개 + 우리만 가능한 것 1개 이상**

**문장 쓰는 규칙**

| 항목 | 규칙 |
|---|---|
| 신호 문장 | 본 것을 그대로 말하는 구어체. `~했어요`, `~가 멈췄어요`. 12~24자 |
| 주체 표시 | 누가·무엇이 달라졌는지 문장에 넣는다 |
| 쓰지 않는 표현 | 시스템 말투(`미제출 2건 발생`), 단정적 평가(`문제`·`위험`), AI 자기소개(`AI가 분석했습니다`), 확률·정확도 수치, 사과 문구 |
| 애매하면 안 띄운다 | 근거가 부족하면 알림을 만들지 않는다. `잘 모르겠어요` 같은 알림은 만들지 않는다 |

### 3.2 근거는 두 가지다

| 구분 | 답하는 질문 | 누가 만드나 | 성격 |
|---|---|---|---|
| **왜 지금 떴는지** | 이 알림이 뜬 이유 | **시스템 규칙만.** AI 안 씀 | 규칙에 걸린 사실. 숫자·날짜·건수. 나중에 다시 확인할 수 있어야 함 |
| **왜 이 초안인지** | 이 초안을 쓴 근거 | 시스템이 정보를 모으고 → AI가 문장으로 | 초안의 재료. 여기 모으는 정보 목록이 곧 "필요한 정보" 칸의 내용 |

**근거를 쓸 때 지킬 것 4가지**

| 항목 | 내용 | 이렇게 쓰지 말고 → 이렇게 |
|---|---|---|
| **한 줄에 한 사실** | 근거 한 줄 = 사실 하나 + 출처 하나 | `진척이 낮다` → `핵심결과 "전환율 개선" 진척 42%` |
| **비교 기준 붙이기** | 숫자만 있으면 이상한지 알 수 없다 | `42%` → `42% (팀 평균 71%)` |
| **언제 기준인지 쓰기** | 모든 근거에 기준 시점을 붙인다 | 나중에 "그때 왜 그랬나"를 확인할 수 있다 |
| **3~5줄** | 그보다 길면 접어 둔다 | 그 이상은 안 읽힌다 |

**비교 기준은 아래 4가지 중 하나를 골라 적는다.**

1. **본인의 예전 기록** (지난 분기·지난 점검 대비)
2. **같은 팀·같은 직무 평균**
3. **계획 대비** (기간이 얼마나 지났는지 대비 진행 정도)
4. **제도 기준값** (규정으로 정한 기준)

**공통 요구** — 근거 한 줄마다 **어느 기록에서 나온 것인지**를 함께 적는다(목표 번호, 핵심결과 번호, 점검 번호 등). 나중에 확인하는 일, 알림 기록과 맞춰 보는 일, 알림에서 해당 화면으로 바로 넘어가는 기능이 전부 이 표시에서 나온다.

### 3.3 행동은 6가지다

| # | 행동 | 무엇을 하나 | 결과가 어디에 남나 | 주로 쓰는 주체 |
|---|---|---|---|---|
| A1 | **쓰기** | 초안을 받아 확인하고 확정 | 새 기록 (진행 점검·자기평가·목표) | 조직원 |
| A2 | **고치기·맞추기** | 이미 있는 내용을 수정 | 기존 기록 수정 + 수정 이력 | 조직원, 1차 |
| A3 | **보내기** | 사람에게 메시지 전달 | 메시지 기록 + 보냄·받음 기록 | 1차, 2차, HR |
| A4 | **대화 잡기** | 1on1·목표 검토 회의 (이야기할 항목 포함) | 일정 + 이야기할 항목 기록 | 1차, 2차 |
| A5 | **들여다보기** | 행동이 아니라 판단하기 전 확인 | **남는 것 없음 (조회만)** | 2차, HR·경영진 |
| A6 | **요청하기** | 등급 조정 회의·재검토·제도 개입 요청 | 요청 기록 + 승인 흐름 | 2차, HR·경영진 |

**결과가 남지 않으면 알림을 만들지 않는다**

> 행동을 하면 시스템 어딘가에 기록이 남아야 한다. **남을 곳이 없으면 그 알림은 만들지 않는다.**

이건 실제로 겪은 문제다. 기존 시연용 화면에서는 상당수 동작이 "완료됐습니다" 안내만 띄우고 아무 데도 저장되지 않았다(다면진단 작성, 주간 업무보고, 일부 평가 제출). 사용자는 처리했다고 믿는데 시스템은 모르는 상태가 된다.

**최종 확정은 사람이 한다**(P6). A5(들여다보기)만 조회이므로 바로 실행해도 된다. 그 외에 사람 확인 없이 진행되는 동작은 없다.

**들여다보기만 남는 것을 경계** — 2차 평가자·HR·경영진 알림은 A5로 도망가기 쉽다. 칸마다 A5가 아닌 행동을 **최소 1개** 두는 것을 조건으로 한다.

### 3.4 신호 한 건은 7가지 항목으로 정의한다

개발자가 그대로 만들 수 있는 최소 단위. **신호 1건 = 아래 7가지가 다 채워진 한 줄.**

| # | 항목 | 내용 |
|---|---|---|
| 1 | 변화의 종류 | ①~⑤ 중 무엇 |
| 2 | 무엇을 보는지 | 어느 정보의 어느 항목 |
| 3 | 어떤 조건일 때 띄우는지 | 판단 조건 + 비교 기준 |
| 4 | 누구에게 띄우는지 | 대상자 + 위로 올릴 때의 조건 3가지 판정 |
| 5 | 너무 자주 뜨지 않게 하는 조건 | 재알림 간격 · 상위 알림 생략 · 처리 시 삭제 · 최소 건수 |
| 6 | 초안을 쓰려면 무엇을 읽어야 하는지 | AI에 넣을 정보 목록 |
| 7 | 무슨 행동을 하게 하고 어디에 남기는지 | 행동 종류(A1~A6) + 저장 위치 + 초안 문장 틀 |

### 3.5 몇 개를 훑어야 하나

```
4단계 (목표수립 · 중간점검 · 평가 · 피드백)
  × 4주체 (조직원 · 조직장1차 · 조직장2차 · HR·경영진)
  = 16칸
  × 변화의 종류 5가지
  = 80번 확인
```

**확인 방법** — 칸 하나를 고르고 ①~⑤를 차례로 물어본다: *"이 사람이 이 단계에서, 이런 종류의 변화 중 알고 싶어할 게 있나?"*
없으면 없다고 적는다(억지로 채우지 않는다). 빈칸이 남는 건 결과이며, 왜 비었는지를 적어 두면 그게 다음 단계의 할 일 목록이 된다.

## 4. 최종 산출물 — 엑셀 파일 1개

파일명: `성과관리Agent_신호카탈로그.xlsx`

**하나의 파일에 신호 → 근거 → 행동이 한 줄로 이어지게 담는다.** 비개발자는 왼쪽 몇 칸만 읽어도 무슨 알림인지 알 수 있고, 개발자는 오른쪽 칸을 보고 만들 수 있게 나눈다.

### 4.1 시트 구성 (4장)

| 시트 | 이름 | 담는 것 |
|---|---|---|
| 1 | **00_읽는법** | 이 파일의 목적, 시트 안내, 용어 풀이, 색·기호 설명 |
| 2 | **01_신호목록** | 본체. 한 줄 = 알림 1건. 주체별·단계별로 걸러 볼 수 있게 |
| 3 | **02_칸점검** | 16칸이 얼마나 채워졌는지 한눈에 보는 표 |
| 4 | **03_문장·기록규칙** | 문장 쓰는 규칙 + 알림 기록으로 남길 항목 |

### 4.2 `01_신호목록` 열 구성 (22열)

읽는 사람이 헷갈리지 않게 **네 묶음**으로 나누고, 묶음마다 머리글 색을 달리한다.

**[묶음 1] 어떤 알림인가 — 누구나 읽는 부분**

| 열 | 이름 | 입력 방식 | 예시 |
|---|---|---|---|
| A | 알림 번호 | `단계-주체-순번` | `중간점검-조직원-01` |
| B | 성과관리 단계 | 목록 선택 | 목표수립 / 중간점검 / 평가 / 피드백 |
| C | 주체 | 목록 선택 | 조직원 / 조직장(1차) / 조직장(2차) / HR·경영진 |
| D | 변화의 종류 | 목록 선택 | ① 때가 됐다 ~ ⑤ 무슨 일이 생겼다 |
| E | 화면에 뜨는 문장 | 직접 작성 (12~24자) | `진행 점검이 3주째 비어 있어요` |
| F | 왜 지금 떴는지 | 직접 작성 | `마지막 점검 후 21일 경과 (팀 평균 8일)` |

**[묶음 2] 무엇을 보고 판단하나 — 개발자가 만드는 부분**

| 열 | 이름 | 입력 방식 | 예시 |
|---|---|---|---|
| G | 판단 조건 | 직접 작성 (사람 말로) | `마지막 점검일로부터 21일 이상 지났고, 목표 기간이 아직 남아 있을 때` |
| H | 비교 기준 | 목록 선택 | 본인 예전 기록 / 팀 평균 / 계획 대비 / 제도 기준값 / 없음 |
| I | 필요한 정보 | 직접 작성, `;` 로 구분 | `점검 기록의 마지막 작성일; 목표 기간; 같은 팀의 점검 이력` |

**[묶음 3] 무엇을 하게 하나**

| 열 | 이름 | 입력 방식 | 예시 |
|---|---|---|---|
| J | 초안 재료 | 직접 작성, `;` 로 구분 | `내 목표의 현재 진척; 최근 활동 기록; 지난 점검에 쓴 문장` |
| K | 행동 | 목록 선택 (A1~A6) | `A1 쓰기` |
| L | 사용자에게 물어보는 문장 | 직접 작성 | `이대로 진행 점검할까요?` |
| M | 결과가 저장되는 곳 | 직접 작성 | `진행 점검 기록 신규 생성` |

**[묶음 4] 채택 여부와 알림 조절**

| 열 | 이름 | 입력 방식 | 예시 |
|---|---|---|---|
| N | 도움 점수 | 1~3 | `3` |
| O | 빈도 점수 | 1~3 | `3` |
| P | 우리만 가능 점수 | 1~3 | `1` |
| Q | 합계 | 수식 `=N+O+P` | `7` |
| R | 판정 | 수식 + 목록 | `기초` / `우리만 가능` / `제외` |
| S | 재알림 간격 | 직접 작성 | `7일` |
| T | 최소 건수 | 직접 작성 | `해당 없음` (개인 알림) / `3건 이상` (합쳐 보는 알림) |
| U | 언제 사라지나 | 직접 작성 | `점검을 저장하면 즉시` |
| V | 비고·확인 필요 | 직접 작성 | `마지막 작성일 보관 여부 확인 필요` |

**입력을 편하게 하는 장치**

- B·C·D·H·K·R 열은 **목록 선택**(엑셀 데이터 유효성)으로 만들어 표기가 흔들리지 않게 한다
- 1행은 고정하고 필터를 걸어 **주체별·단계별로 걸러 보게** 한다
- R열이 `제외`면 그 줄 전체를 회색으로 (조건부 서식)
- M열(저장되는 곳)이 비면 빨간색으로 — **여기가 비면 그 알림은 만들 수 없다**
- V열에 내용이 있으면 노란색으로 — 담당자에게 물어볼 목록이 자동으로 모인다

### 4.3 `02_칸점검` 구성

4주체(열) × 4단계(행) = 16칸. 각 칸에 세 가지를 적는다.

| 표기 | 내용 | 방법 |
|---|---|---|
| 알림 개수 | 이 칸에 채택된 알림 수 | `01_신호목록`에서 자동 집계 (COUNTIFS) |
| 구성 | 기초 몇 개 / 우리만 가능 몇 개 | 자동 집계 |
| 비었으면 사유 | 왜 없는지 한 줄 | 직접 작성 |

목표는 칸마다 **기초 1개 + 우리만 가능한 것 1개 이상.** 미달인 칸은 색으로 드러나게 해서, 검토 자리에서 바로 "이 칸이 비었다"를 이야기할 수 있게 한다.

### 4.4 `03_문장·기록규칙` 구성

두 부분으로 나눈다.

**(1) 문장 쓰는 규칙** — §3.1의 문장 규칙과 좋은 예·나쁜 예. 여러 사람이 나눠 쓰더라도 알림 말투가 하나로 유지되게 하는 기준.

**(2) 알림 기록으로 남길 항목** — 알림이 뜨고 나서 무엇을 남길지. 규칙으로 만든 알림은 나중에 성적을 봐야 고칠 수 있다.

| 묶음 | 남길 것 | 여기서 알 수 있는 것 |
|---|---|---|
| ① 떴을 때 | 알림 번호, 규칙 버전, 뜬 시각, 어느 시점 기준인지 | 규칙을 고쳤을 때 전보다 나아졌는지 |
| ② 누구에게 | 대상자, 주체 구분, 범위(본인/팀원/팀/조직) | 주체별로 알림이 몇 개씩 가는지 |
| ③ 무엇을 보고 | 변화의 종류, 본 기록, 판단 결과값 | 어떤 종류가 헛알림이 많은지 |
| ④ 근거 | 사실·숫자·비교 기준·출처·기준 시점 | 근거를 펼쳐 보는 비율 |
| ⑤ 행동과 결과 | 행동 종류, 초안 생성 여부, 보낸 시각, 열어본 시각, 결과(확정/고쳐서 확정/무시/기한 지남), 저장된 기록 | 확정 비율, 고쳐서 확정한 비율, 무시 비율, 열고도 아무것도 안 한 비율 |
| ⑥ 안 띄운 경우 | 안 띄운 이유, 다시 띄울 수 있는 시각, 대신 뜬 상위 알림 | 알림을 잘 줄이고 있는지 |

**이 기록이 왜 필요한가** — 생성형 AI는 문장을 고쳐서 성능을 올릴 수 있지만, 규칙은 그렇게 못 한다. *어떤 알림이 열리고, 실제로 처리되고, 무시되는지*를 남기지 않으면 규칙은 첫 버전에 그대로 머문다.

**⑤에서 읽는 신호**

| 수치 | 낮거나 높으면 |
|---|---|
| 열어본 비율이 낮음 | 문장이 안 끌리거나 알림 채널이 안 맞음 |
| 근거를 펼쳐 본 비율이 낮음 | 근거를 볼 필요 없는 알림 = 굳이 없어도 되는 알림 |
| 고쳐서 확정한 비율이 높음 | 초안 재료(J열)가 부족함 |
| 무시 비율이 높음 | 띄우는 조건이 너무 예민함 |
| 열고도 아무것도 안 한 비율이 높음 | 무엇을 해야 하는지가 불분명함 |

## 6. 개발자에게 넘길 때

**넘기는 것** — 엑셀 파일 1개. 별도 문서 없음.

**개발자가 보는 곳**

| 무엇을 만들 때 | 어느 열을 보나 |
|---|---|
| 알림을 띄울지 판단하는 규칙 | G(판단 조건) · H(비교 기준) · D(변화의 종류) |
| 어떤 정보를 읽어야 하는지 | I(필요한 정보) · J(초안 재료) |
| 누구에게 띄우는지 | C(주체) |
| 몇 번 띄우고 언제 없앨지 | S · T · U |
| 화면에 뜨는 문장 | E · F · L |
| 처리 결과를 어디에 저장할지 | M(결과가 저장되는 곳) |
| 무엇을 기록으로 남길지 | `03_문장·기록규칙` (2)번 표 |

**넘기기 전에 확인할 것 3가지**

1. **M열(결과가 저장되는 곳)에 빈칸이 없다.** 빈칸이면 개발자가 만들 곳이 없다는 뜻이므로, 제외하거나 "새로 만들어야 함"으로 적어 함께 넘긴다
2. **V열(확인 필요)이 `00_읽는법` 아래에 모여 있다.** 개발자가 질문할 곳을 찾아 헤매지 않게 한다
3. **G열의 판단 조건이 한 문장으로 읽힌다.** 전문 용어 없이도 조건이 뭔지 알 수 있어야, 검토하는 사람과 만드는 사람이 같은 것을 본다

**바뀔 때** — 규칙을 고치면 `03_문장·기록규칙`의 "규칙 버전"을 올린다. 그래야 알림 기록에서 고친 전후를 비교할 수 있다.

## 부록. `01_신호목록` 작성 예 (1줄)

형식을 보여주기 위한 예시이며, 실제 내용은 작업 순서 3~9에서 채운다.

| 열 | 값 |
|---|---|
| A 알림 번호 | `중간점검-조직원-01` |
| B 단계 | 중간점검 |
| C 주체 | 조직원 |
| D 변화의 종류 | ② 비어 있다 / 멈췄다 |
| E 화면 문장 | 진행 점검이 3주째 비어 있어요 |
| F 왜 지금 | 마지막 점검 후 21일 경과 (팀 평균 8일) |
| G 판단 조건 | 마지막 점검일로부터 21일 이상 지났고, 목표 기간이 아직 남아 있을 때 |
| H 비교 기준 | 팀 평균 |
| I 필요한 정보 | 점검 기록의 마지막 작성일; 목표 기간; 같은 팀의 점검 이력 |
| J 초안 재료 | 내 목표의 현재 진척; 최근 활동 기록; 지난 점검에 쓴 문장 |
| K 행동 | A1 쓰기 |
| L 물어보는 문장 | 이대로 진행 점검할까요? |
| M 저장되는 곳 | 진행 점검 기록 신규 생성 |
| N·O·P / Q | 3 · 3 · 1 / 7 |
| R 판정 | 기초 |
| S 재알림 간격 | 7일 |
| T 최소 건수 | 해당 없음 |
| U 언제 사라지나 | 점검을 저장하면 즉시 |
| V 확인 필요 | 점검 기록의 마지막 작성일이 시스템에 남는지 확인 |
