> 목표 설정부터 평가까지 — 경영진·HR운영자·일반사용자 3 페르소나별 신호 제안과 생성형 에이전트
> - 경영진 뷰 — 목표 간 정렬이 흐트러진 조직 신호를 먼저 짚어줌
> - 일반사용자 뷰 — 체크인 시점, 유관 목표 변경 등 놓치기 쉬운 신호를 알림
> - 리더의 1:1 준비 — 최근 워크로드·목표 진척 신호를 결합해 코칭 포인트 자동 제안

전제 하나가 더 있다 — **신호는 규칙이 만들고, 그 신호에서 사용자가 더 물으면 그때 Claude 가 이어서 답한다.
그 두 층을 사용자가 화면에서 구분할 수 있어야 한다.**

## 1. 진단 — 왜 지금은 3 페르소나가 아닌가

카탈로그 150건의 `roles` 는 세 갈래뿐이다.

| roles | 건수 | actor |
|---|---|---|
| `["member"]` | 40 | 구성원 |
| `["leader"]` | 72 | 팀장 40 + 상위조직장 32 |
| `["hr","exec"]` | 38 | HR경영진 |

`hr` 만 또는 `exec` 만 가진 신호는 **0건**이다. 엔진의 유일한 하드 필터
(`ez_signal_engine.js` `forRole()`)가 `roles.indexOf(rk)` 이므로 **HR과 경영진은 같은 38건을
같은 순서로** 받았다. 정렬도 `actorNo → stageNo → no`, 곧 카탈로그 나열 순서였다 —
유형(T1~T5)은 정렬에 쓰이지 않았고 `score.freq`·`score.unique` 는 어디서도 읽히지 않았다.

즉 시놉시스가 요구한 "경영진은 목표 정렬을, HR은 평가 편차를 먼저 짚어준다"가
**코드에 존재하지 않았다.**

## 2. 고침 — 감추지 않고 순서를 바꾼다

`js/ez_signal_persona.js` 신설 (`window.EZPersona`).

- 카탈로그를 **자르지 않는다**. 열람은 150건 그대로다(누가 무엇을 못 보게 되는 변화가 아니다).
- 같은 목록을 그 사람이 그 자리에서 먼저 볼 순서로 **정렬**한다.
- 걸리는 자리는 `ez_signal_engine.js` `live()`·`pending()` **정렬 한 곳**. 알림 탭·FAB 배지·
  선제 팝업·추천 질문이 전부 그 함수를 거치므로 표면마다 따로 손대지 않는다.
  `EZPersona` 가 없으면 예전 순서로 그대로 돈다.

| 관점 | 렌즈 한 줄 | 무게 |
|---|---|---|
| 조직원 | 내 차례인 일 | 중간점검·T1 기한·T5 변동 · 「체크인」「상위 목표」「마감」 |
| 조직장 | 1:1 전에 볼 것 | 중간점검·T2 공백 · 「1on1」「면담」「장애요인」「확신도」「초과근무」 |
| HR | 공정성 먼저 | 평가·T3 기준 이탈 · 「등급」「분포」「상한」「편차」「제출」「근거」 |
| 경영진 | 목표 정렬 먼저 | 목표수립·중간점검·T4 연결 불일치 · 「정렬」「미연결」「상위 목표」「전략」「격차」 |

계기판 `node scripts/check_signal_persona.js` — ① HR·경영진 상위 5건 겹침 ≤ 2건
② 경영진 상위 5건 전부 정렬 계열 ③ HR 상위 5건 전부 평가·피드백 운영·공정성 계열. 실패하면 exit 1.

실측(2026-08-03):

```
[hr]   공정성 먼저   1. 조직 14곳 상위 등급 비중이 최고 80%, 최저 25%예요
                    2. A등급 한 칸이 75%로 상한 65%를 넘어요
                    4. 마감 2일 앞 전사 1차 평가 제출률이 12%로 기준 85%에 못 미쳐요
[exec] 목표 정렬 먼저 1. 전사 상위 목표 연결률은 95%인데 한 조직만 목표 41%가 미연결이에요
                    2. 지표가 목표값 아래인 전략 테마 세 곳에 걸린 목표가 9건이에요
                    3. 세 조직에서 하위 진척은 4주 동안 18%p 올랐는데 상위는 1%p예요
겹침 0건
```

알림 탭 머리에 `.ezx-sig-lens` 한 줄(렌즈 이름 + 설명)을 둔다 — 같은 38건을 받는 두 사람이
왜 다른 순서로 보는지 사용자가 알 수 있게. **순위 점수·유형 코드·단계 이름은 화면에 쓰지 않는다**(R2 유지).

## 3. 규칙이 센 답 ↔ elizax 가 이어서 한 답

두 층이 한 대화에 나란히 쌓이는데 구분 표시가 하나도 없었다. 계통(`.ezx-msg.ai > .ezx-bubble`)은
하위 모듈(근거칩·후속칩·피드백) 호환 때문에 통일해 둔 것이므로 **클래스만 더한다**.

| 층 | 표시 | 어디 |
|---|---|---|
| 규칙 | 말풍선 왼쪽 회색 레일 + 머리 한 줄 「규칙으로 확인한 결과 · 지금 기록으로 직접 셌어요」 | `buildSigNode` → `.ezx-msg.ai.sig-rule`, `.sg-src` |
| elizax | 말풍선 왼쪽 액션 컬러 레일 | 알림에서 이어진 모델 답 → `.ezx-msg.ai.from-sig` |

실계산이 안 되는 신호는 머리 줄이 「아직 기록이 모이는 중이에요」로 바뀐다 — 규칙이 셌다고
거짓말하지 않는다.

**넘어가는 자리**를 단추로 만든다. 처리 단추 뒤, 「이 알림 자세히」 앞에
`✦ elizax에게 더 묻기`(테두리 단추 = 채움 처리 단추와 테두리 열람 단추 사이의 세 번째 격).
누르면 `EZSignalChat.arm(id)` 로 주제를 못 박고 질문을 보낸다 — 그래야 그 알림의 근거가
payload 에 실린다(「더 묻기」 문장만으로는 어느 알림인지 낱말로 알 수 없다).

곁들여 고친 것 — `followAnswer` 가 `scrub()` 만 거쳐 카탈로그 문안의 `{{팀원명}}` 이 화면에
그대로 나갔다. `phrase()` 로 바꾸고, 그것만으로는 「어떤 팀원」 이라는 뭉갠 말이 남아 바로 위
알림 문구(「박영희님 …」)와 어긋나므로 **엔진이 알림 문구에 박아 둔 이름을 초안에도 물려 준다**
(`nameOf(inst)`).

## 4. HR 현장 용어로 되돌린다

지적: *"우리 팀 목표에 안 붙은 팀원 목표가 있는지 봐줘"* 가 아니라
*"우리 팀 목표와 정렬(align)되지 않은 팀원의 목표가 있는지 봐줘"* 여야 한다.
구어로 풀어쓰다 HR 도메인 용어가 사라졌다.

원천이 둘이라 두 방향을 함께 맞춘다.

| 원천 | 무엇 | 방향 |
|---|---|---|
| `elizax_docs/성과관리Agent_신호카탈로그_v0.6.json` | 알림 문구·판단 조건·근거 줄·기준값·처리 초안 | 여기서 고쳐 `build_signals.py` → `js/ez_signals.js` |

  말투(반말 요청체)는 유지하고 **용어만** 바꿨다. 길이 18~36자·중복 0·라우팅 어긋남 0 유지

  **번호가 아니라 이름으로** 찾게 바꿨다(20차에 「부르는 질문」 열이 끼면서 뒤 열이 한 칸 밀려 있었다).

## 6. 역할 부적합 연결

「부하직원이 상사를 평가하는 화면은 연결되면 안 된다」는 기준으로 성과 사이클 화면을 전수 감사했다.
**조직원이 상사를 평가하는 화면은 없었다**(평가 작성은 member 일 때 본인 자기평가 한 행뿐,
「평가 검토」 탭은 제거됨). 그러나 다른 종류의 어긋남이 있었다.

| # | 무엇이 잘못 | 고침 |
|---|---|---|
| 1 | 성과관리 › 피드백 탭이 정적 마크업이라 조직장·HR·경영진 화면에 **타인이 받은 피드백 원문**이 그대로 남았다(`tx_hydrate` 가 조기 반환, `patchFeedback` 은 in-place 패치) | `feedbackLog` 에서 `to_emp === 나` 만 골라 전면 재생성, 0건이면 빈 상태 |
| 2 | 360 진단 카드가 `anon:'비공개'` 인데도 **평가자 실명**을 상시 표시. 대상자 드롭다운은 조직장에게도 전사 80명 | 공개가 아니면 익명 아바타 + 「평가자 N명」, 드롭다운은 조직장=팀 범위·조직원=차단 |
| 3 | 상향 피드백이 `EZPolicy.ANON_MIN`(3) 을 안 거쳐 **응답 2명**인 건이 근거 카드에 노출. 같은 줄에서 `themes` 객체 배열을 그대로 이어 붙여 `[object Object]` 출력 | 임계 필터 추가 + `.map(t => t.label)` |
| 4 | 경영진 화면의 「2차 등급 조정」·「결과 확정」 담당자가 **경영진 본인 이름**(실제 담당은 HR) | `hrRep()` 기준으로 바꾸고 경영진은 열람 전용 |
| 5 | 조직원도 「목표 맵」을 열어 **전 조직 트리 + 전사 40명 실명**을 볼 수 있었다(목표 화면의 member 차단을 우회) | 조직원은 버튼 미렌더 + 트리 루트를 소속 조직으로 + 구성원 목록을 소속 조직으로 |
| 6 | 「내가 열람할 수 있는 1:1」 탭이 동료의 아젠다·노트·액션 **원문**을 보여줬다(`tx_policy` 는 「확정 요약만」으로 규정) | 확정 요약 한 줄 + 열람 범위 고지만 |

## 7. 남긴 것

- 카탈로그 `roles` 자체를 `hr`/`exec` 로 쪼개지 않았다. 원천(v0.6 JSON)의 수신 주체는
  「HR경영진」 한 칸이고, 그것을 둘로 가르는 것은 카탈로그 개정 사안이다.
  제품은 **렌즈로** 가른다 — 원천을 건드리지 않고 같은 결과를 낸다.
- `score.freq`·`score.unique` 는 여전히 미사용. 렌즈가 단계·유형·낱말로 대신 판단한다.
- 화면 렌더러가 아직 안 쓰는 실데이터가 남아 있다 — `evalStatus` 221 · `meetingStore` ·
  `evaluatorMap` · `gradeHistory` · `krProgress`. 지금 소비처는 신호 판정 함수뿐이다.
  화면의 하드코딩 날짜·이름을 이 데이터로 옮기는 것이 다음 과제다.
